\section{Solucions i eines existents}

Les solucions més properes al TFM no formen una única categoria. Les cues
operatives resolen l'execució de treball backend; les biblioteques de simulació
aporten primitives temporals; i algunes eines visuals faciliten definir cues o
workflows. La comparació s'ha de fer segons la seva relació amb la plataforma
prevista, no segons la quantitat de funcionalitats que ofereixen.

BullMQ gestiona tasques i workers sobre Redis i admet FIFO, LIFO i prioritats
\parencite{bullmqPrioritized}. RabbitMQ és un broker de missatges amb cues FIFO
i cues amb prioritat subjectes al tipus de cua i a la configuració
\parencite{rabbitmqPriority}. Ambdues són referències directes del domini
backend, però executen treball real sota una configuració concreta. No estan
orientades a repetir una mateixa càrrega amb diverses polítiques i presentar-ne
una comparació experimental neutral.

SimPy proporciona processos, esdeveniments i recursos per construir
simulacions en Python \parencite{simpyTime}. És una referència útil per entendre
el rellotge virtual, però no ofereix per si sola la gestió d'escenaris, les
polítiques del TFM, la persistència ni la interfície web. SimuQ és un antecedent
més proper perquè combina una interfície amb la simulació de sistemes de cues
mitjançant SimPy \parencite{caballero2016simuq}; tanmateix, representa punts de
servei i es presenta com una aplicació d'escriptori, no com una plataforma web
per analitzar tasques backend.

n8n permet definir i executar workflows mitjançant una interfície visual. En
mode cua, una instància principal registra les execucions i workers independents
les processen mitjançant Redis \parencite{n8nQueueMode}. Aquesta arquitectura
és rellevant com a exemple de plataforma web d'automatització, però la seva cua
gestiona execucions reals. El node d'espera suspèn un workflow durant un interval
real o fins que es compleix una condició \parencite{n8nWait}; no proporciona el
rellotge virtual ni la comparació de FIFO, prioritat estricta i envelliment que
requereix el TFM. Implementar tota aquesta lògica en un node de codi convertiria
n8n en un contenidor del motor, no en el motor mateix.

Els simuladors acadèmics de Grid, cloud o computació distribuïda constitueixen
antecedents metodològics, però no són alternatives directes al producte. El TFM
no pretén reproduir els seus models d'infraestructura, sinó aplicar un model
acotat dins d'una experiència web orientada a configurar i interpretar
comparacions de polítiques.

La revisió no identifica una eina que integri el domini de les tasques backend,
un motor temporal controlat, polítiques intercanviables i una comparació web de
resultats. Aquest espai és el que delimita la plataforma proposada.
